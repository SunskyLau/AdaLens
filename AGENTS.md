# Repository Guidelines

## Project Structure & Module Organization
This repo is split into `backend/` and `frontend/`. The Python backend entrypoints live in `backend/cli.py` and `backend/main.py`, with core orchestration and models under `backend/framework/`. Backend tests live in `backend/test/`. The React/Vite frontend lives in `frontend/src/`, organized by `components/`, `pages/`, `server/`, `store/`, `api/`, and `utils/`. Sample data is stored in `data/`, and frontend contract notes live in `frontend/docs/`.

## Build, Test, and Development Commands
- `cd backend; python main.py` runs the backend against `data/vgsales.csv`.
- `cd backend; python -m pytest -q` runs the backend test suite.
- `cd frontend; npm run dev` starts the Vite client on `http://localhost:5173` and the Run Gateway on `http://localhost:3001`.
- `cd frontend; npm run build` type-checks with `tsc` and produces a production bundle in `frontend/dist/`.
- `cd frontend; npx tsx --test src/**/*.test.ts src/**/*.test.tsx` runs the frontend tests with TypeScript support.

## Coding Style & Naming Conventions
Use 4 spaces in Python and keep type hints where the module already uses them. Follow the existing dataclass-heavy backend style and keep modules focused (`framework/models.py`, `framework/master_agent.py`, etc.). In the frontend, use TypeScript with strict settings, single quotes, and semicolons. Use `PascalCase` for React components (`ConversationPanel.tsx`), `camelCase` for helpers (`workspaceLiveSync.ts`), and colocated `*.test.ts` or `*.test.tsx` files for tests. Prefer the `@/` alias for frontend imports from `src/`.

## Testing Guidelines
Add or update tests with every behavior change. Backend tests use `pytest` discovery over `unittest`-style test cases in `backend/test/test_*.py`. Frontend tests use Node's test runner via `tsx`; keep tests next to the code they cover and name them `*.test.ts(x)`. Favor small focused tests for layout helpers, store logic, CLI behavior, and API contracts.

## Commit & Pull Request Guidelines
Recent history follows Conventional Commit style: `feat(scope): ...`, `fix(scope): ...`, `refactor: ...`. Keep messages imperative and use a scope when it clarifies the area changed, for example `fix(storyline): auto-refit on summary append`. PRs should describe the user-visible change, list verification commands run, link the related issue when applicable, and include screenshots or short recordings for frontend/UI changes.

## Agent-Specific Notes
Check for nested guidance before editing specialized areas. In particular, `frontend/src/components/AGENTS.md` defines additional rules for storyline visualization work.

## Current Product Semantics
- Runs are resumable while `status` is `running`, `paused`, `idle`, or `completed`; plan-level control now includes `pause`, `resume`, and `terminate`.
- A paused plan stays visible in the product as an in-progress plan, and resuming it must not require deleting or rewriting the existing `backend/framework/sub_agent.py` main flow.
- Storyline steering now writes only canonical action kinds `focus`, `ignore`, `elaborate`, and `create`; historical `dive_into`, `cut_off`, and `suppress` values remain read-compatible for replay/import only.
- Automatic planning and fallback planning must never create a new plan by reusing the current turn goal text, any prior user-authored message text, or any existing plan text once a run already has plans. Non-`create` steering no longer hard-blocks runtime fallback or stage-summary evaluation; instead each such steering records whether a later related `create_plans` call has happened, unresolved steering follow-ups must stay visible in the master-agent prompt, `evaluate_progress` may still happen before they are handled when justified, and `mark_complete` should only happen after those open steering follow-ups have been addressed.
- Storyline steering creation uses a persistent smaller toolbar in the storyline top-left, laid out vertically with `focus`, `ignore`, and `elaborate` pens plus the implicit no-pen state. The pen toolbar and all of its internal content are intentionally compact; the pen buttons still share one compact width sized for the pen labels and keep the icon/text content centered. Clicking the active pen again, switching pens, switching runs, closing/canceling a steering popover, pressing `Esc`, or successfully confirming a pen request after it has been sent to the backend clears the current pen mode.
- With no active pen, storyline keeps its existing selection and filter interactions. With an active pen, column clicks remain steering-only; summary-area and atomic-glyph clicks still replay their normal local selection/chat-link behavior while also opening the steering flow.
- `focus` / `ignore` pens may target columns, summary areas, and atomic glyphs. Column pen hit areas include converge lanes, converge endpoint markers, converge indicators, boundary branches, and summary-internal tracks. Clicking a column target now stages a persistent toggleable multi-column set immediately, reuses one live confirmation popover, stores only `target.columns` in first-click order, and never writes or depends on any `anchor column` / `target.column_name` semantics. Historical `column_name` payloads are read-compatible only and must not affect behavior.
- Summary areas and atomic glyphs now carry summarizer-generated `keywords` metadata. For summary/glyph `focus` / `ignore`, the UI opens a keyword chooser populated from those keywords, plus an editable `Preview` textarea and a read-only `Background` block seeded from the summary/atomic text. The `Background` header shows an `Included` label with a checkbox that controls whether that background is appended to `user_prompt`, defaulting to checked; unchecked background blocks must switch to a visibly excluded style instead of staying identical. The old free-form `Other` input is removed. When stored keywords exist the confirmed request stores at least one selected keyword in `selected_keywords`; older runs may omit `keywords`, in which case steering still works through the `Preview` / `Background` flow alone. The chat card shows the selected keywords first when present, followed by a `Target` section, and its `Preview` details block shows the user-visible `user_prompt` only.
- The editable `Preview` keeps the current `generated prefix + preserved appended text` model: target/keyword/column changes may refresh the generated prefix, but the user-appended portion must remain stable and must not be rewritten by later refreshes. While that generated portion is present, the auto-filled topic keywords, selected columns, and summary/atomic target text inside `Preview` render as colored bold text. For summary/glyph `focus` / `ignore`, generated preview templates now start directly with keyword-priority wording and no longer include fixed lead-ins such as `请继续围绕该总结开展后续分析` / `Focus follow-up analysis on this summary`, `请继续围绕该原子洞察开展后续分析` / `Focus follow-up analysis on this atomic insight`, `请降低后续对该总结的分析优先级` / `Ignore future follow-up analysis on this summary`, or `请降低后续对该原子洞察的分析优先级` / `Ignore future follow-up analysis on this atomic insight`.
- Storyline converge indicator font sizing now uses only that converge's immediate right-turn atomic counts: `0` counts stay at the current minimum font size, the maximum nonzero count stays at the current maximum font size, intermediate nonzero counts use linear interpolation, and when all nonzero counts in the same converge are identical those nonzero lanes all use the arithmetic midpoint font size.
- `elaborate` only targets summary areas and atomic glyphs. It never targets columns, does not support multi-select, and opens a confirmation popover instead of the keyword chooser. Its meaning is: keep investigating that one specific insight, especially its root causes and explanation, while avoiding unnecessary branching into multiple new plans.
- `elaborate` chat/popover cards render a compact `Target` section only; atomic targets may show short label plus atomic text, while summary targets omit the full summary background. Column `focus` / `ignore` chat/popover cards render only a `Column` section with the selected column names.
- In pen mode, hovering a valid column target keeps the existing column-hover rendering. Pen activation must not alter summary-area or atomic-glyph hover behavior: summary hover still shows the lightweight summary preview card, and glyph hover still shows the atomic hover preview card without any pen-only border treatment.
- Hovering an active plan area below `50%` zoom still shows the lightweight plan preview card containing only the first sentence that is otherwise hidden at that zoom, but this low-zoom plan hover card remains suppressed while a pen is active.
- Left-clicking storyline blank space without dragging must clear the current storyline selection. Blank-space drag keeps the existing pan interaction and must not clear selection.
- Pen-triggered `focus` / `ignore` / `elaborate` popovers are draggable from non-interactive blank space inside the card (not from keyword chips, text inputs, checkboxes, or action buttons) and must stay clamped within the storyline viewport after dragging. Blank-space `create` popovers now use the same blank-space drag behavior and viewport clamping.
- Right-clicking blank storyline space still opens a `create` composer. Submitting it immediately adds exactly one user-authored plan. If the latest dispatch batch still has any nonterminal plan (`pending`, `analyzing`, `summarizing`, or `paused`), that new plan must join that current unresolved batch immediately. If that batch still has free execution capacity, the new plan should begin running right away without resuming or disturbing older paused/pending siblings; otherwise it remains `pending` inside that batch until capacity opens. Only when all existing dispatch batches are already fully terminal (`completed`, `failed`, or `terminated`) should `create` first persist as an unbatched pending plan in `MasterAgentState.pending_direct_user_create_dispatch_plan_ids`; after the immediate acknowledgement is emitted, a synthetic `dispatch_plans` call must become the only path that opens the new create dispatch batch / `dispatch_turn_index`. New runs must not add a separate create user chat card; the create plan should appear only through dispatch UI, while older runs may still render historical create steering cards.
- Clicking a create-origin active plan area should keep the plan-selection highlight while also highlighting and scrolling to the corresponding dispatch entry in chat when one exists; only older runs without that dispatch anchor may fall back to the historical `create` steering message.
- Selecting a directly user-created summary area should keep its normal summary-card chat linkage only and must not add an extra highlight bridge to a `create` steering message.
- The directly user-created active plan area and the directly user-created summary area use the `create` accent border styling; later automatically derived follow-up work does not inherit that accent, and their text keeps the default non-create font color.
- Storyline renders active plan areas inside their real dispatch turn, not in a synthetic extra turn. These plan areas share the same visual card language as chat-side dispatched plan cards, stay bidirectionally linked with chat selection/focus, allow click-again deselection in storyline, keep plan-control buttons fully inside the card border on the status row's right side, show only the first sentence of the plan text without the chat-only plan-id / `Open analysis stream` rows, treat English abbreviation periods such as `e.g.` / `i.e.` as non-terminal punctuation for that truncation, hide plan text below `50%` X zoom, and stop shrinking horizontally once the status row reaches its readable minimum width.
- Active plan area placement must not perturb already-solved summary / converge geometry for that turn; pack active plans into the remaining same-turn vertical space after summary/converge solving rather than re-solving the historical summary band around them.
- As new summary areas or active plan areas appear during a run, storyline keeps the current viewport/zoom and must not force re-centering. Automatic fit is limited to initial run/viewport-fit situations.
- The workspace header shows a `Sub-agents` concurrency slider immediately to the left of the run-status pill whenever a run exists. Its canonical range is `1-6`, its default is `2`, changes persist to `RunSettings.max_concurrency` immediately, and those changes only affect the next dispatch / later seat-fill decisions rather than preempting the current batch on their own.
- Plan-level `start` / `resume` requests must also respect the same `max_concurrency` hard cap. When all execution seats are occupied, the request may update latest-batch ordering but must not launch additional active work until a seat becomes available.
- Automatic pending seat-fill is terminal-event-driven: `completed` / `failed` / `terminated` transitions may backfill waiting `pending` siblings only when execution capacity is available, while plain `paused` must never trigger that search on its own.
- Only the latest unresolved dispatch batch is reorderable in storyline. Dragging current-batch active plan areas immediately rewrites that batch's live order for both chat and storyline; the top `max_concurrency` nonterminal plans in that new order become the active execution seats, any displaced `analyzing` / `summarizing` plan immediately returns to `pending` with `control_state='yield_requested'`, and newly admitted `pending` / `paused` plans immediately take over those seats.
- Active storyline plan areas in `analyzing` / `summarizing` state use a stronger pulsing border treatment so currently running work is visually obvious.
- Summary selection keeps line-highlighting local to the selected summary's nearest left/right converges and margin branches. Summaries that share dataset columns with the selected summary should stay undimmed even though line propagation remains local.
- Storyline turn/converge boundary layout now uses local `ordering -> alignment -> compaction` windows. Except for the leftmost special case, `turn_i` is solved only from `converge_i`, `converge_{i+1}` is solved only from `turn_i`, ingress summary-local left boundaries are order-only contracts, and already solved ingress converges may only receive a final whole-band centering shift rather than a later local re-solve.
- Boundary-window insertion/compaction now lets later-ingress extension columns land above the old top lane, below the old bottom lane, or between preserved lanes; ingress stage 3 compacts the full ordered converge band (old lanes plus extension lanes) together, keeps summary-local left-port `d1/d2` independent from converge-lane compaction, sizes ingress converge `d1` to include current indicator-clearance needs so labels do not collide, and preserves already-legal large inter-cluster gaps during egress compaction instead of collapsing them upward.
- Summary-local route-box safety is now geometry-driven in X as well as Y: slot/interspace minimum widths are derived from route-box and branch geometry, low-zoom turns may rerun wider when dense large-route-box summaries need more horizontal clearance, and high-zoom extra turn width should remain mostly as internal gutter rather than uniformly stretching every summary-local slot.
- Summary-area short labels intentionally use a noticeably larger baseline font while still following the existing area-size-driven scaling logic.
- Summary-area short labels must never use horizontal glyph compression; if a short label cannot fit, expand the owning summary area (and turn width) instead of squeezing text.
- Atomic hover shows an enlarged lightweight preview card only while the glyph is hovered; clicking a glyph no longer pins or fixes a storyline atomic card.
- Every new user-authored `chat`, `focus`, `ignore`, `elaborate`, or `create` input must trigger exactly one immediate runtime-generated `respond_to_user` acknowledgement before the master agent runs any other tool. That one-time acknowledgement must be cleared once emitted and must not repeat on later loops. Healthy-path acknowledgements must come from the dedicated fast LLM path using the full canonical user-authored message plus steering metadata, not from a truncated `96`-character excerpt/template path.
- Explicit stop/finish-intent `chat` inputs are not ordinary follow-up steering: the fast acknowledgement model path must return both the immediate acknowledgement text and an internal `probable_stop` routing signal for that chat. After a chat is marked `probable_stop`, runtime should stop pending/paused work from starting, let already-running work finish naturally, bypass post-steer follow-up-plan requirements, and then end the run through normal master-agent completion semantics rather than generic planning. Their immediate acknowledgement must say the run will stop/wrap up, not falsely claim the stop has already completed. While stop-completion is pending, any model- or fallback-proposed `evaluate_progress`, `synthesize_findings`, or ordinary `mark_complete` must be filtered out. Once current work is terminal, stop-intent completion must not emit a stage summary card; runtime should allow exactly one internal stop-completion `mark_complete` final summary for the whole run.
- Every dispatch batch must also emit exactly one separate `respond_to_user` when that batch first becomes fully terminal (`completed` / `failed` / `terminated` for every plan in the batch), even if no stage summary is emitted for that batch. This batch-finished reply is distinct from both the immediate acknowledgement reply and the post-summary reply, and it must not repeat after resume/reload.
- Every `evaluation` / `mark_complete` summary must still be followed immediately by one separate `respond_to_user`, explaining both why the stage/final summary is justified now and what follow-up analysis directions still make sense. That post-summary reply should stay concise (roughly 1-3 sentences), must stay in the language of the latest user-authored request/steer/create message, and when it cites summary/atomic evidence it should reuse the same inline citation logic as stage/final summaries. If the model omits, misorders, leaves that response empty, or replies in the wrong language, the backend must auto-inject a fallback response.
- No other standalone `respond_to_user` calls are part of the runtime contract beyond: immediate acknowledgement for each new user-authored input, one batch-finished reply per dispatch batch, and the required post-summary / post-completion reply.
- `dispatch_plans.result.plan_ids` is now the full ordered membership of the current dispatch batch, while `dispatch_plans.result.dispatched_plan_ids` is only the subset that actually started in that dispatch step.
- Summarizer-produced `summary` text must strip stock lead-in first sentences such as `The analysis reveals...` / `根据您的要求...` and start directly from the substantive conclusion.
- Summarizer normalization must treat Chinese sentence-ending punctuation (`。`, `！`, `？`) as terminal punctuation. Backend output for `summary` and `atomic_insights[].text` must not append an extra English period after those marks (avoid mixed endings like `。.` / `！.` / `？.`).
- For historical runs that already persisted mixed endings (for example `。.`), gateway/frontend read normalization should sanitize those sequences in displayed summary and atomic text so legacy data renders cleanly without migration.
- Stage/final summaries map back onto storyline converges through `dispatch_turn_index`: each converge may show full-width summary buttons derived from those entries, with stage-summary buttons above that converge's own current topmost indicator geometry and final-summary buttons below that converge's current lowest visible indicator geometry, including extension markers when they are the highest/lowest visible reference. Both placements reuse the same intentionally roomier clearance rule. Clicking a button must first clear current storyline selection, then request chat focus for the matching summary card while forcing `stickToBottom=false` before the focus scroll starts, so the jump is not pulled back to bottom. Converge summary buttons keep hover/pressed emphasis but no longer persist a post-click highlighted style. Below `50%` zoom those buttons become icon-only while keeping their color coding and full-width layout. Backend stage summaries may only be considered after every current plan in the run is already terminal; a single finished batch is not sufficient by itself. Each emitted stage summary still attaches to the latest covered `dispatch_turn_index` for placement, but its content scope must cover every still-unsummarized retained finding since the previous stage summary or final summary, not just the latest completed batch.
- Any change to master-agent runtime sequencing, dispatch-batch membership rules, `create steering` behavior, or legal `respond_to_user` trigger points must update this document and the matching backend tests in the same change.
- In chat, `Plans Created` is collapsed by default, `thinking` entries are collapsed by default, completed / failed / terminated dispatched-plan cards collapse to a status-row-only header by default and expose a chevron affordance for manual expansion/collapse while still auto-expanding for the selected plan or selected summary unless the user explicitly re-collapses them, the `x tool(s) invoked` count stays visible even while collapsed, tool chips appear only when a thinking entry is expanded, and raw machine-only JSON such as `{\"tool_names\": [...]}` stays hidden.
- `PlanItem` no longer carries legacy plan `depth` or motivation metadata in the run-state contract, and the old backend trace sidecar has been removed.
- Inline citations such as `[[1]], [[2,7]]` must remain render-safe, and clicking them must not trigger delayed chat auto-scroll while analysis is still ongoing.
- `respond_to_user` messages may also carry inline citations, and those citations must bind to the same storyline summary / atomic activation, focus, highlight, and centering behavior used by stage/final summary citations.
- The chat `Back to bottom` button keeps its existing visual styling but lives above the dataset-upload region, and the composer uses `Enter` to send with `Shift+Enter` / `Ctrl+Enter` reserved for newlines. After a user sends a chat input or successfully submits a steering action, chat should auto-scroll to the latest message.
